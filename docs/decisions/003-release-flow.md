# 003 · Release flow

- **Date:** 2026-11-11
- **Origin:** spike [#67](https://github.com/lauvivans/haru/issues/67), before setting up versions ([#20](https://github.com/lauvivans/haru/issues/20)) and the first release to `main`
- **Status:** proposed

## Question

Which tool creates Haru's versions, tags and release notes, and can it also cut the `release/<version>` branch?

## Short answer

- **Two small workflows of our own, no release tool**, the same as Gaku's decision 008. A manual "Cut release" workflow cuts `release/<version>` from `develop` and opens the pull request to `main`. Merging that pull request runs the release workflow, which runs CI, tags the version, publishes the GitHub release and deploys production.
- **The version comes from the commits on `develop`.** The cut workflow reads the Conventional Commits since the last tag and computes the next version. An optional input sets the version by hand, for example `1.0.0` when the beta ends.
- **The first release is `0.1.0`.** While the version is `0.x`, a breaking change or a `feat` bumps the minor and anything else bumps the patch.
- **Release notes live in the GitHub release**, generated by GitHub from the merged pull requests. There is no `CHANGELOG.md` and no version commit on `main`.
- **Pull request titles are checked with commitlint**, because the squash commit takes the title and the version rule reads it.

## Options compared

| Option                          | Who cuts `release/<version>` and picks the version                                                              | Pull requests per release                       | Commits on `main` to merge back                 | `0.1.0` and breaking changes in `0.x`                      | Release notes  |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------- | -------------- |
| release-please                  | A person cuts the branch; the tool computes the version again on `main`, which can differ from the branch name | 2 (release branch, then the release-please PR) | Every release (`CHANGELOG.md` and the manifest) | Supported, with `bump-minor-pre-major`                     | `CHANGELOG.md` |
| semantic-release                | A person cuts the branch; the tool picks the version on `main`                                                  | 1                                               | None                                            | Not supported: its FAQ says starting at `0.0.1` is not supported | GitHub release |
| Manual tags and generated notes | A person does every step                                                                                        | 1                                               | None                                            | A person picks the version                                 | GitHub release |
| Manual workflow (chosen)        | The workflow cuts the branch and computes the version                                                           | 1                                               | None                                            | Our own rule, written below                                | GitHub release |

release-please fits a flow where `main` takes pull requests directly. With a release branch in front of it, every release needs a second pull request on `main`, a commit on `main` that must be merged back into `develop`, and a version the tool decides after the branch already has a name. Pointing it at `develop` with `target-branch` moves the version commit there, but the release branch then has to wait for the release-please pull request, so each release still takes two pull requests. Its pull request is opened with `GITHUB_TOKEN`, so CI on it waits for approval unless a personal access token is added.

semantic-release is ruled out by the version: its FAQ says starting at `0.0.1` "is not supported by semantic-release" and leaves the `0.x` rules of SemVer out of scope.

Manual tags give the same result with no code, but every release repeats the same steps by hand. The chosen workflows automate them and keep a single place where the version is decided. They are also the same as Gaku's, so both projects release the same way.

## Release flow

1. **Cut.** Run the "Cut release" workflow (`workflow_dispatch`) on `develop`. It computes the version, pushes `release/<version>` and opens the pull request to `main` titled `chore(release): <version>`, with a `Closes #<issue>` line for every issue its commits close.
2. **Freeze and fix.** `develop` keeps taking pull requests. A fix found in QA goes in a pull request to `release/<version>`.
3. **Release.** Merge the pull request with a merge commit. The release workflow runs when a pull request from `release/<version>` is merged into `main` and reads the version from the branch name. It stops if the name doesn't match `release/X.Y.Z`, then runs CI, creates the tag `v<version>` and the GitHub release with generated notes, and deploys production, as jobs of the same workflow.
4. **Merge back.** Only when the release branch got a fix: merge `main` into `develop`.

A hotfix follows the same steps from `main`: a `release/<patch version>` branch cut from `main` by hand, a pull request to `main`, then the merge back into `develop`.

## Version rule

The cut workflow takes the highest `v*` tag in the repository, sorted by version (`git tag --list 'v*' --sort=-v:refname`), and reads the full messages of the commits in `<tag>..develop`. It can't use the nearest tag (`git describe`): the tag sits on the merge commit in `main`, which `develop` only reaches after a merge back.

| Commits since the last tag                                            | While `0.x` | From `1.0.0` |
| --------------------------------------------------------------------- | ----------- | ------------ |
| A breaking change (`!` in the subject or a `BREAKING CHANGE:` footer) | Minor       | Major        |
| A `feat`                                                              | Minor       | Minor        |
| Anything else (`fix`, `chore`, `docs`)                                | Patch       | Patch        |

With no tag yet, the version is `0.1.0`. A release is always a choice made by a person, so a release with only `chore` commits, such as dependency updates, still gets a patch version. Leaving `0.x` is done by hand with the version input.

## Tokens

Events caused by `GITHUB_TOKEN` don't start other workflows, except `workflow_dispatch` and `repository_dispatch`. A pull request opened with it starts runs that wait for approval. That shapes the flow:

- The deploy is a job in the release workflow, so it doesn't need a workflow triggered by the tag or the release.
- The release workflow starts from the merge, which a person makes, so it runs normally.
- CI on the release pull request waits for a click to approve it. The same commits already passed CI on their pull requests to `develop`, and the release workflow runs CI again before deploying.

No personal access token is needed.

## Consequences

- #20 is rewritten for these workflows and keeps the commitlint check on pull request titles.
- `production.yml` (deploy on every push to `main`) is replaced by the release workflow. `ci.yml` and `deploy.yml` take the ref to check out, since a closed pull request event doesn't point at the merge commit by default.
- The repo setting "Allow GitHub Actions to create and approve pull requests" is turned on for the cut workflow.
- The release steps go into the Workflow section of `CLAUDE.md`.
- `package.json` has no version field to keep in sync. The tag is the version.
- The first release should confirm that the generated notes list the pull requests merged into `develop`, and not only the release pull request. If they don't, the cut workflow writes the notes from the commit subjects instead.
